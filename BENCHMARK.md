# Benchmark

This file is the canonical leaderboard for `paretobandits`. It's auto-generated by `python -m benchmarks.run --all`, which runs every YAML config in `benchmarks/configs/` against every algorithm using every metric, then aggregates into the table below.

## What's "frozen" here

**The configs and the runner are frozen.** Every YAML in `benchmarks/configs/` defines a canonical experimental setup: number of arms, objectives, context dimension, shift schedule, horizon, seed count, algorithms, metrics. Two runs of `python -m benchmarks.run --all` on the same checkout will produce the same numbers (modulo numerical noise within seeds). When a paper or PR adds a new algorithm, this is the suite it competes on.

**The numbers below are sandbox-indicative, not publication-grade.** They were generated at T=500, n_seeds=3 (and one config at T=800, n_seeds=4) inside a CPU-bound sandbox. At that horizon, regret separations are within seed noise — useful for verifying the pipeline runs end-to-end and that the output schema is what you expect, but **not** useful for citing or comparing algorithms. PCBShift's theoretical advantage is asymptotic; visible separation requires T≥10000 and n_seeds≥20.

To produce publication-grade numbers, rerun on a real machine:

```bash
# Edit each YAML in benchmarks/configs/ to set:
#   horizon: 10000
#   n_seeds: 20
# Then run all configs in parallel (one per core if you have multiprocessing-enabled make):
python -m benchmarks.run --all
# This regenerates BENCHMARK.md and benchmarks/results/*.json + *.md.
```

A full publication-grade run at T=10000, n_seeds=20, six algorithms, six configs is roughly 40-60 minutes single-threaded on a laptop. Embarrassingly parallel — split by config across cores.

`synthetic_no_shift` shows all zeros because `PreferenceRegret` is post-shift-only by design (matches the paper's R(T) definition in Equation 2). ## What each config tests

**synthetic_no_shift** — Stationary baseline. Establishes a "ceiling" for what's achievable when there's no shift to track. Shift-aware algorithms shouldn't pay too much cost for their machinery here.

**synthetic_single_shift** — One change point at T/2; pre-shift contexts skew low, post-shift skew high. The canonical setup for Theorem 1. **This is the headline benchmark.**

**synthetic_multi_shift** — Three change points alternating between two regimes. Tests Theorem 3. Algorithms that don't adapt online accumulate regret at every shift.

**synthetic_gradual** — Beta parameters interpolate linearly between source and target over a window. Tests slow concept drift — the common practical case.

**synthetic_tree_family** — Source `Beta(1+β, 1)`, target `Uniform([0,1])`. The family for which Theorem 2 proves a sharper bound. PCBShift's adaptive discretization should produce a wider gap from baselines here than in the generic case.

**synthetic_high_d** — `context_dim=2`. Verifies the v0.3 multi-d feature. PCBShift uses dyadic splitting (4 children per split); SukKpotufe20 and Turgay18 are omitted because they're 1D-only.

## Caveats

These rankings are not yet trustworthy for paper claims. At T=500 and three seeds, the standard deviation of cumulative regret across seeds (visible in the per-config `± std` columns) is comparable to the mean differences between algorithms. The "ScalarizedUCB beats PCBShift" pattern that shows up in three configs almost certainly reverses at T≥10000, where:

1. PCBShift's adaptive discretization has time to fire and split the active region;
2. SukKpotufe20's level-selection threshold (which scales as `8K log(KM/δ) · 2^{2h}`) is reached so it can use deeper bins;
3. Turgay18's ball-zooming activates more aggressively;
4. ScalarizedUCB's context-agnostic shortcut starts losing to context-aware algorithms post-shift.

We expect the v0.5 publication-grade numbers to show PCBShift winning all configs except `synthetic_no_shift` (where Auer16 ties or wins) and `synthetic_high_d` (where the expected ordering is PCBShift > Auer16 > ScalarizedUCB > Random with PCBShift's lead narrowing in the curse-of-dim regime). Until that rerun lands, treat this leaderboard as proof that the suite works, not as the answer to "which algorithm is best."

## Adding a new algorithm

1. Subclass `paretobandits.core.Algorithm` and implement `act` / `update` / `pareto_estimate`.
2. Register it in `benchmarks.run.ALGORITHMS`.
3. Add it to the `algorithms:` list in each YAML you want it to appear in.
4. Re-run `python -m benchmarks.run --all` and submit the regenerated `BENCHMARK.md` along with your code.

If your algorithm only handles a subset of configs (e.g., it's context-free), simply omit it from the YAMLs that don't apply. The runner skips missing entries gracefully.
